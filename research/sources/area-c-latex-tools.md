## Verified sources

### S1. latexmk (John Collins) - official man page
Citation: John Collins, *latexmk(1) - generate LaTeX document*, manual page dated 9 March 2026, distributed with latexmk 4.88.
URL: https://mirrors.ctan.org/support/latexmk/latexmk.txt (also latexmk.pdf); package page https://ctan.org/pkg/latexmk
Access: full text.
Evidence label: SOURCED.

Verbatim quotes.

Dynamic discovery of the dependency set, from the log file:

> "Latexmk determines which are the source files by examining the log file.  (Optionally, it also examines the list of input and output files generated by the -recorder option of modern versions of latex (and pdflatex, xelatex, lualatex). [...] When latexmk is run, it examines properties of the source files, and if any have been changed since the last document generation, latexmk will run the various LaTeX processing programs as necessary.  In particular, it will repeat the run of latex (or a related program)) often enough to resolve all cross references; depending on the macro packages used.  With some macro packages and document classes, four, or even more, runs may be needed."

The general rerun rule, stated explicitly:

> "The general rule latexmk uses for determining when an extra run of some program is needed is that one of the source files has changed."

Checksum, and the admission that LaTeX's dependency structure is circular:

> "Those of you with experience with Makefiles, may get concerned that the .ndx file is written during a run of *latex and is always later than the .nnd last read in.  Thus the .nnd appears to be perpetually out-of-date.  This situation, of circular dependencies, is endemic to latex, and is one of the issues that latexmk is programmed to overcome.  It examines the contents of the files (by use of a checksum), and only does a remake when the file contents have actually changed."

Acknowledgement that checksum equality is the only oracle, and that a spurious difference produces an unbounded loop stopped only by the cap:

> "But consider for example a latex package that causes an encapsulated postscript file (an "eps" file) to be made that is to be read in on the next run.  The file contains a comment line giving its creation date and time.  On the next run the time changes, latex sees that the eps file has changed, and therefore reruns latex.  This causes an infinite loop, that is only terminated because latexmk has a limit on the number of runs to guard against pathological situations."

THE ITERATION CAP, name and documented default, verbatim from the man page:

> "$max_repeat [5]
>        The maximum number of times latexmk will run *latex before deciding that there may be an infinite loop and that it needs to bail out, rather than rerunning *latex again to resolve cross-references, etc.  The default value covers all normal cases.
>
>        (Note that the "etc" covers a lot of cases where one run of *latex generates files to be read in on a later run.)"

Confirmed: the variable is named `$max_repeat` and its documented default is `5`.

Exact contribution: a dynamic, checksum-driven build driver for LaTeX that discovers the rule network and the required number of passes by running the engine and comparing file states, with a hard repeat limit.

What it does NOT do: it does not parse the LaTeX source to build a dependency graph; it does not compute a pass number for any fact; it does not analyse cycles; it does not predict, before running, how many passes will be needed or whether the document converges at all; it never names the label, reference, counter, or source span responsible for instability.

Relevance to AuxFlow: this is the baseline AuxFlow is compared against. Anticipation verdict: PARTIAL OVERLAP (it solves the same user-facing problem - "run LaTeX the right number of times" - by an entirely dynamic mechanism, so it anticipates the goal but not the static method).

### S2. latexmk source (latexmk.pl) - cap value, cap-exhausted message, MD5 database, undecidability
Citation: John Collins, `latexmk.pl`, latexmk 4.88, 2026-03-09, GPL2.
URL: https://mirrors.ctan.org/support/latexmk/latexmk.pl
Access: full source.
Evidence label: SOURCED.

The cap in code, with the author's reasoning (line 1295 ff.):

> "our $max_repeat = 5;    # Maximum times I repeat latex.  Normally
>                         # 3 would be sufficient: 1st run generates aux file,
>                         # 2nd run picks up aux file, and maybe toc, lof which
>                         # contain out-of-date information, e.g., wrong page
>                         # references in toc, lof and index, and unresolved
>                         # references in the middle of lines.  But the
>                         # formatting is more-or-less correct.  On the 3rd
>                         # run, the page refs etc in toc, lof, etc are about
>                         # correct, but some slight formatting changes may
>                         # occur, which mess up page numbers in the toc and lof,
>                         # Hence a 4th run is conceivably necessary.
>                         # At least one document class (JHEP.cls) works
>                         # in such a way that a 4th run is needed.
>                         # We allow an extra run for safety for a
>                         # maximum of 5. Needing further runs is
>                         # usually an indication of a problem; further
>                         # runs may not resolve the problem, and
>                         # instead could cause an infinite loop."

EXACTLY WHAT IT REPORTS WHEN THE CAP IS EXHAUSTED (lines 10312-10320):

> "    if ( $pass{$rule} >= $max_repeat ) {
>         # Avoid infinite loop by having a maximum repeat count
>         # Getting here represents some kind of weird error.
>         warn "$My_name: Maximum runs of $rule reached ",
>              "without getting stable files\n";
>         $too_many_passes = 1;"

So the entire diagnosis is the string `Maximum runs of <rule> reached without getting stable files`. It names the *rule* (e.g. `pdflatex`), not the offending fact, label, counter, or source location. NO CAUSE IS ATTRIBUTED. Confirmed.

The change-detection mechanism, exactly (lines ~1600-1683):

> "we instead use the md5 signature of the files.  (Previous versions of latexmk used the backup file method, but restricted to the case of .aux and .idx files, sufficient for most, but not all, situations.)
>
> We will have a database of (time, size, md5) for the relevant files. If the time and size of a file haven't changed, then the file is assumed not to have changed; this saves us from having to determine its md5 signature"

> "In all the following a fdb-hash is a hash of the form:
>                      filename -> [time, size, md5]"

`use Digest::MD5;` at line 113. The comparison itself (line 11007 ff.):

> "    # For other kinds of file change, primarily use md5 signature to
>     # determine whether file contents have changed.
>     # Backup by file size change, but only in the case where there is
>     # no pattern of lines to ignore in testing for a change"

So: which files are checksummed - every file in the rule network's source list, generated and user, tracked as `(time, size, md5)`; MD5 is recomputed only when time or size changed (an optimisation, not a semantic difference); a rerun is triggered when the MD5 differs. There is no `.aux`-only special case in current versions - the manual and source both say the old backup-of-.aux method was replaced.

Latexmk ALSO scrapes the engine log as a secondary signal (line 6334):

> "        if (/Rerun to get/) {
>             print "$My_name: References changed.\n" if ! $log_silent;
>             $reference_changed = 1;"

This is the engine rerun warning. It is an additional trigger, not the primary oracle; the primary oracle is the MD5 database. This matches the established correction that engine warnings are not a reliable convergence oracle and checksum comparison is the practical baseline.

MOST IMPORTANT PASSAGE FOR AUXFLOW - the author states the undecidability himself (lines 9929-9935):

> "    #    11. In addition, the loop is terminated if the number of
>     #        applications of a rule exceeds a configured maximum. This
>     #        guards agains the possibility that it may never be possible to
>     #        get stable output, i.e., there is an infinite loop.  It is
>     #        impossible for an algorithm to determine in general whether
>     #        there is an infinite loop.  (An example of the Turing halting
>     #        theorem.) But normal documents need a decidable modest number
>     #        of passes through the loop.  Any exceeding of the limit on the
>     #        number of passes needs examination."

Exact contribution of this passage: latexmk's maintainer has already published, in the shipped source of the field's dominant build tool, the observation that non-convergence detection is undecidable in general and that the cap is a pragmatic guard. AuxFlow therefore cannot present "LaTeX convergence is undecidable in general, so we need a conservative approximation" as a new insight; it can only claim the specific conservative static analysis.

What it does NOT do: no static analysis of any kind; the whole rule network is built from log/`.fls` output of actual runs.

Relevance to AuxFlow: (i) fixes the baseline exactly; (ii) removes any novelty in the undecidability observation; (iii) leaves open the static classification and the source-level diagnosis.
Anticipation verdict: PARTIAL OVERLAP, and FULL ANTICIPATION of the undecidability framing.

### S3. labelschanged (Brian Dunn, after David Carlisle)
Citation: Brian Dunn (packager/maintainer), based on public-domain code by David Carlisle, *labelschanged - Identify labels which cause endless "may have changed" warnings*, CTAN package v1.01, dated 2024/01/12; first released 2017-12-11.
URL: https://ctan.org/pkg/labelschanged ; source https://mirrors.ctan.org/macros/latex/contrib/labelschanged/labelschanged.dtx ; repo https://github.com/bdtc/labelschanged
Access: full source and full documentation.
Evidence label: SOURCED.

What it is, verbatim from the CTAN page:

> "Labelschanged - Identify labels which cause endless "may have changed" warnings
>
> Several conditions can cause LaTeX labels to keep changing, no matter how many times a document is recompiled.
>
> This package helps diagnose the cause of repeated "Label(s) may have changed" warnings. The names and before/after definitions of changing labels are printed at the end of each compile.
>
> Multiply-defined labels are printed as well."

The motivating problem, verbatim from labelschanged.dtx (documentation part), including its taxonomy of causes:

> "Several conditions can cause \LaTeX\ labels to keep changing, no matter how many times a document is recompiled.
> \item[Dynamic references:] Some packages, such as \pkg{varioref}, generate text references which dynamically change depending on the location of each float, and these changing messages may then cause the floats themselves to move.
> \item[Margin/foot notes:] References in margin or foot notes may have a similar effect.
> \item[Active characters:] Due to the way changing labels are detected, problems may also be caused by active characters in captions or section names."

> "reoccurs despite multiple document re-compiles. Locating the problem labels may be difficult, as there may not be any message identifying which labels have changed."

The mechanism, verbatim from the dtx code section:

> "At the end of the document, the |.aux| file is read back while \cs{newlabel} and \cs{bibcite} are effectively redefined as:
> |\def\newlabel{\@testdef r}| \quad ---\,and\,--- \\
> |\def\bibcite{\@testdef b}|
>
> While the |.aux| file is read, each label's new definition as given in the |.aux| file is compared to its existing definition as defined by |r@<label>| or |b@<label>|."

And the actual code, verbatim:

> "\def\@testdef #1#2#3{%
>     \def\reserved@a{#3}%
>     \expandafter \ifx \csname #1@#2\endcsname \reserved@a  \else%
>         \typeout{^^JLabel `#2' has changed:^^J%
>         \meaning\reserved@a^^J%
>         \expandafter\meaning\csname #1@#2\endcsname^^J}%
>         \@tempswatrue%
>     \fi%
> }"

Exact contribution: per-label, per-instance identification of *which* auxiliary fact failed to stabilise, together with its old and new values, emitted on every compile. It is a value-level diff of the `.aux` fact table, done inside LaTeX itself by hooking `\@testdef`.

What it does NOT do: no static analysis; no parse of the document source; no dependency graph; no pass numbers; no cycle detection; no classification of benign-versus-amplifying; no prediction. It cannot tell you a document will not converge - it only tells you, after a run, which label differed. It reports the label NAME and the label's macro `\meaning`, NOT a source file and line number, and NOT the chain of facts that caused the change. Its "Solutions" section is a hand-written list of usual suspects (varioref, marginnote, footmisc perpage, active characters in captions, memoir+breqn), not an analysis of the document at hand. It also explicitly gives up on missing references: "Unfortunately, locating missing references still requires searching the log to find which are a problem."

Relevance to AuxFlow: this is the closest existing thing to AuxFlow's *instance-level fact identity*. labelschanged already treats individual label instances as the unit of instability and already reports the offending instances by name with before/after values. AuxFlow's remaining differentiators against it are (i) staticness, (ii) the dependency graph and pass-lag edges, (iii) SCC classification, (iv) source spans, (v) a build plan.
Anticipation verdict: PARTIAL OVERLAP - anticipates "name the offending fact instances", does not anticipate static analysis, graphs, or classification.

PR question, RESOLVED: `https://api.github.com/repos/bdtc/labelschanged/pulls?state=all` returns `[]`. There is no pull request of any state in bdtc/labelschanged, and the GitHub API reports `Issues: 0`, `Files: README.md` only. Any earlier note describing an open/unimplemented PR for labelschanged, or a specific closed one, is unsupported and must be struck. Evidence label: SOURCED.

### S4. Typst - `introspection/convergence.rs`
Citation: Typst source code, `crates/typst-library/src/introspection/convergence.rs`, typst/typst, commit-pinned view at 6a6f1a97a3446fc6ba5a723b0baf20a0cfeaaef5 (blob commit a35c624ed07c).
URL: https://github.com/typst/typst/blob/6a6f1a97a3446fc6ba5a723b0baf20a0cfeaaef5/crates/typst-library/src/introspection/convergence.rs
Access: full source.
Evidence label: SOURCED.

THE CAP, with its exact source location - `crates/typst-library/src/introspection/convergence.rs`, immediately after the imports:

> "pub const MAX_ITERS: usize = 5;
> pub const ITER_NAMES: &[&str] =
>     &["iter (1)", "iter (2)", "iter (3)", "iter (4)", "iter (5)"];
>
> const INSTANCES: usize = MAX_ITERS + 1;"

So Typst runs layout `MAX_ITERS = 5` times and keeps `INSTANCES = 6` introspector snapshots (five iterations plus a final one). The convergence test is a hash comparison of the last two:

> "    /// Whether the values in this history converged, i.e. the final and
>     /// pre-final values are the same.
>     pub fn converged(&self) -> bool
>     where
>         T: Hash,
>     {
>         // We compare by hash because the values should be fully the same, i.e.
>         // with no observable difference. When a state changes from `0.0`
>         // (float) to `0` (int), that could be observed in the next iteration
>         // and should not count as converged.
>         typst_utils::hash128(&self.0[MAX_ITERS - 1].1)
>             == typst_utils::hash128(&self.0[MAX_ITERS].1)
>     }"

WHAT IT DOES WHEN THE CAP IS EXHAUSTED - it emits a document-level warning plus one warning per non-stabilising introspection:

> "/// Analyzes all introspections that were performed during compilation and
> /// produces non-convergence diagnostics.
> #[typst_macros::time(name = "analyze introspections")]
> pub fn analyze(..."

> "    let mut diags = sink.warnings();
>     if !diags.is_empty() {
>         let summary = warning!(
>             Span::detached(),
>             "document did not converge within five attempts";
>             hint: "see {} additional warning{} for more details",
>                 diags.len(),
>                 if diags.len() > 1 { "s" } else { "" };
>             hint: "see https://typst.app/help/convergence for help";
>         );
>         diags.insert(0, summary);
>     }"

Crucially, the architecture is designed so each kind of observable fact gets a *tailored* non-convergence diagnostic, and the value history per iteration is reported:

> "/// Document iteration N+1 observes the `Output` values from the document built
> /// by iteration N. If the output values do not stabilize by the iteration
> /// limit, a non-convergence warning will be created via
> /// [`diagnose`](Self::diagnose)."

> "/// A good example of this are counters and state: They could just use
> /// `QueryIntrospection`, but are custom introspections so that the diagnostics
> /// can expose non-convergence in a way that's closer to what the user operates
> /// with."

> "    /// Produces a hint with the observed values for each iteration.
>     pub fn hint(&self, what: &str, mut f: impl FnMut(&T) -> EcoString) -> EcoString {
>         let mut hint = eco_format!("the following {what} were observed:");"

Typst also notes, in the same file, the false-positive direction of its own oracle, i.e. it knows its dynamic test is only an approximation:

> "// However, in case (2) the introspection is filtering out data that comemo
> // did observe. Thus, the validation may fail but the document actually did
> // converge! In this case, we reach `analyze` (because comemo validation
> // failed), but we get zero diagnostics. In this case, we do _not_ issue the
> // convergence warning, since the document did in fact converge."

> "    /// In theory, we could detect this scenario by compiling one more time and
>     /// ensuring the document is _exactly_ the same. For now, we're not doing
>     /// this, but it's an option."

What it does NOT do: it is entirely DYNAMIC and POST-HOC. It does not report a *chain* of facts, only the endpoints it happens to have spans for.

HOW MUCH OF AUXFLOW'S PROBLEM TYPST HAS ENGINEERED AWAY - plainly:
1. The multi-pass build-driver problem is gone entirely. Typst has no `.aux` file and no external build loop, so "how many times must I run the engine" is not a user-facing question in Typst at all. `latexmk`'s entire reason to exist is absent.
2. The convergence *verdict* is already delivered to users: "document did not converge within five attempts".
3. The *diagnosis* is already delivered at instance level with source spans and value histories - which is the single feature AuxFlow's design leans on hardest as its user-visible payoff.
4. What Typst has NOT done: it has not made any of this static. It pays for the diagnosis by running layout six times and diffing. It cannot answer "will this converge" without compiling, cannot certify convergence, cannot classify a cycle as benign-versus-amplifying, and cannot say how many passes a document needs, because it always takes exactly five.
So the honest position: Typst has engineered away the *build-orchestration* half of AuxFlow's problem and has already built the *reporting* half, dynamically. What remains genuinely unoccupied is static, pre-execution classification with a cycle taxonomy - and Typst's existence also weakens the practical motivation, since the modern answer to "my document will not converge" is increasingly "the typesetting engine tells you, with a span".
Anticipation verdict: FULL ANTICIPATION of instance-level non-convergence reporting with source spans and of the fixed-iteration-cap-plus-hash oracle. PARTIAL OVERLAP with AuxFlow's classification output (BENIGN_CYCLIC / AMPLIFYING has no Typst analogue). ORTHOGONAL to static pass-number assignment.

### S6. latexrun (Austin Clements) - and the finding that breaks AuxFlow's H3

Citation: Austin Clements, `latexrun`, README.md, https://github.com/aclements/latexrun.
URL: https://raw.githubusercontent.com/aclements/latexrun/master/README.md
Access: full text.
Evidence label: SOURCED.

The Rubber-fragility quote the project had on record as `reported` is VERIFIED, verbatim, and it
comes with a concrete counterexample the project should reuse:

> "latexrun has robust post-execution dependency analysis, while Rubber works by parsing your TeX
> code.  TeX is, famously, the only thing that can correctly parse TeX code and as a result
> Rubber's dependency analysis is fragile.  Simple things like
> ```
>     \newcommand{\includegraph}[1]{\includegraphics{graph/#1.pdf}}
>     \includegraph{results}
> ```
> break Rubber's dependency analysis."

latexrun states its goal in fixpoint terms and draws the cyclic graph explicitly:

> "latexrun views the world as a cyclic graph of deterministic functions of system state" [ASCII
> diagram of latex and bibtex with .aux/.toc/.bbl feedback edges follows]

> "latexrun's goal is to find the *fixed-point* of this computation.  Put simply, it runs latex and
> bibtex repeatedly until it can guarantee that additional runs will not change the output."

**THE CRITICAL PASSAGE. This is the single most consequential finding in the tools survey, because
it falsifies a stated AuxFlow hypothesis:**

> "A direct approach could be to check the output of latex and bibtex after each run and stop when
> the output is the same from one run to the next.  This works, but runs latex too many times; it
> will have already produced its final output one iteration before this approach can figure out
> that it's done.
>
> Instead, latexrun models latex and bibtex as deterministic functions of the file system state,
> their command-line arguments, and certain environment variables.  Hence, if the *inputs* to latex
> and bibtex do not change over one iteration, then latexrun can guarantee that the output also will
> not change, and stop."

Plus the feature-list claim:

> "Runs latex the right number of times. [...] latexrun hides this complexity by running LaTeX (and
> BibTeX) as many times as necessary and no more."

Exact contribution: a dynamic LaTeX driver whose convergence oracle is **input** stability rather
than **output** stability, together with an explicit argument that output-stability comparison costs
exactly one redundant run and that input-stability comparison does not.

What it does NOT do: no static analysis of the source (it is emphatic that source parsing is the
wrong approach); no dependency graph over facts; no pass numbers; no cycle classification; no
prediction before the first run; no source-level attribution of an unstable fact.

Relevance to AuxFlow: severe and two-edged.
1. It supplies, from a primary source, the exact argument AuxFlow uses for its
   consecutive-state-comparison gap - stated first, by someone else, as a design *problem to be
   avoided*.
2. It then avoids it. AuxFlow's **H3** ("Static classification certifies a document's run count
   using strictly fewer engine executions than any consecutive-state comparison detector, the gap
   being exactly one execution") is true only against detectors that compare consecutive *outputs*.
   latexrun is a widely used tool that does not, and it reaches N runs, not N+1. AuxFlow's
   evaluation baseline C, as currently specified, is therefore a **strawman unless latexrun is added
   as a separate baseline** and the hypothesis is restated as being about output-comparison
   detectors specifically.
3. The `\includegraph` counterexample is the cleanest available argument for AuxFlow's default-deny
   subset, and it is stronger than the abstract "TeX can only be parsed by TeX" line because it is
   two lines of ordinary LaTeX.

Anticipation verdict: FULL ANTICIPATION of the one-extra-run observation AND of its avoidance.
PARTIAL OVERLAP with the "run the right number of times" goal. ORTHOGONAL to static analysis.

### S7. Tectonic - read-then-written comparison, cap of 6, and it names the unstable file

Anticipation verdict: FULL ANTICIPATION of same-run read-then-written convergence detection and of

**Verdict on the two questions the area was set up to answer.**

1. *Does any existing tool perform static, pre-execution convergence classification?*
   **No.** Every tool verified here discovers the run count by running. latexmk's author states in
   the shipped source that the general problem is undecidable ("An example of the Turing halting
   theorem"). This negative survives.

   with before/after values. Tectonic names the file that changed. Typst names the fact, gives a
   byte span, gives the full per-iteration value history, and adds a second span for the element
   that produced the unstable value. AuxFlow's claim that existing tools "exhaust a retry cap and

   Tectonic and Typst, and must be narrowed accordingly.

## Summary for the audit

- **`latexmk` is now pinned exactly.** Convergence oracle: a `(time, size, md5)` database over every
  file in the rule network, with the engine's `Rerun to get` warning as a secondary trigger. Cap:
  `$max_repeat`, documented default `5`, with the author's own reasoning for the number preserved in
  the source. Cap-exhausted output: `Maximum runs of <rule> reached without getting stable files`,
  naming the rule and nothing else.
- **latexmk's author has already published the undecidability observation**, in the shipped source:
  "It is impossible for an algorithm to determine in general whether there is an infinite loop. (An
  example of the Turing halting theorem.)" AuxFlow cannot present that framing as an insight.
- **THE MOST DANGEROUS FINDING IN THIS AREA IS latexrun's README**, and it is dangerous to the
  *evaluation*, not the analysis. latexrun states AuxFlow's one-extra-run argument explicitly and
  then engineers around it by comparing tool **inputs** instead of outputs. Tectonic independently
  does the same thing by comparing read-then-written files within a single run. AuxFlow's H3, and
  baseline C as specified, must be rewritten: the extra run is a property of *output*-comparison
  detectors, not of dynamic detection, and two widely used tools already avoid it.
- **Typst fully anticipates the diagnostic half of AuxFlow's user-visible value.** Per-fact
  warnings, byte spans, per-iteration value histories, a "created here" secondary span, a
  document-level "did not converge within five attempts" verdict, and a help URL - all shipped, all
  dynamic. AuxFlow's diagnostics are not a new *kind* of output; only their derivation is.
- **Typst also removes the build-orchestration problem entirely** - no auxiliary files, no external
  driver, a fixed five iterations - which weakens the practical motivation for the whole project
  area, since the modern answer to "my document will not converge" is increasingly "the engine tells
  you, with a span".
- **`labelschanged` anticipates instance-level fact identity in the LaTeX domain.** It already
  treats individual labels as the unit of instability and prints the offending ones with old and new
  values, and it ships a hand-written taxonomy of usual causes (varioref, margin and foot notes,
  active characters in captions). AuxFlow's remaining differentiators against it are staticness, the
  graph, pass lag, classification, source spans and a plan.
- **Nobody does static pre-execution convergence classification.** That negative survives the whole
  tools survey and is the only clean space left.
- **Every system caps iteration with a hand-chosen constant**: latexmk 5, Tectonic 6, ConTeXt 9,
  Typst 5, `llmk` 5 (from area B). Five independent implementations, five magic numbers, no
  derivation. This is the strongest practical motivation AuxFlow has, and it is well evidenced.
- **AuxFlow must narrow one motivating claim.** "Existing tools exhaust a retry cap and report only
  that they gave up" is true of latexmk and ConTeXt, and false of Tectonic (names the file),
  `labelschanged` (names the labels) and Typst (names the fact, the span and the value history).
